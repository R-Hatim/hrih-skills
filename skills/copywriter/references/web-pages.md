## 1. How people read pages

Most visitors scan before they read. Nielsen Norman Group's classic study found most users scanned rather than read word by word. A version rewritten to be concise, scannable and objective (facts instead of promotional language) tested far more usable.

- Front-load headings, bullets and link text: the first two or three words carry the meaning.
- Make each heading informative on its own. "Cut month-end close from 6 days to 2" beats "Why automation matters".
- Write half the words you first think you need.
- One idea per paragraph. Put the conclusion first.
- Hype words lower credibility. Let facts persuade.
- Clarity beats cleverness. A reader who sees only the headline should know what you sell.

## 2. Hero (above the fold)

A visitor should be able to answer four questions in about five seconds: **What is it? Who is it for? Why should I care? What do I do next?**

| Unit | Job | Notes |
|---|---|---|
| Eyebrow (optional) | The category or audience | "Invoicing for freelance designers" |
| H1 | The one big idea | A concrete outcome or a plain statement of what it is, usually 4–12 words. Write 5+ candidates from different angles and pick with the three questions (picture it / prove it false / only us). Check customer quotes first: the best headline is often already in them |
| Subhead | What it is and why the H1 is believable | 1–2 sentences. Put the specificity the H1 couldn't fit here: the mechanism, a number, the audience |
| Primary CTA | Verb + what they get | "Start free trial", "See pricing for my team", "Get the checklist". Not "Submit"; avoid bare "Learn more" when a specific label fits |
| CTA microcopy | Remove the nearest anxiety | "Free for 14 days. No card needed." only if true |
| Proof near the hero | Real logos, a real customer count, a rating with its source | Or `[NEED: …]`, never invented |
| Visual | Show the product doing the thing | A screenshot beats an abstract illustration; describe what it should show if you're not making it |

**Message match:** if traffic comes from an ad or email, the H1 must continue that promise in similar words.

## 3. Body sections

Use only what the argument needs, in roughly this order. Size each section by how much buyers care, not to make them even.

- **Social proof:** named, specific testimonials that answer an objection ("I was sure migrating would take a week. It took an afternoon.") beat general praise. Never write testimonials yourself. Use the user's real ones, or a clearly marked placeholder.
- **Problem and stakes:** the "before", in customer words. Name it once, honestly; don't wallow.
- **Benefits and features:** 3–6 blocks, each with:
  - a blunt heading that states the value
  - a short paragraph that answers an objection or shows the mechanism
  - proof (a number, a name, a screenshot description)

  Feature → what it lets you do → result → proof.
- **How it works:** 3–4 concrete steps. This lowers perceived effort.
- **Comparison with the alternative:** from positioning. Be fair to the alternative: naming where it's the better fit builds trust.
- **FAQ and objections:** real questions from sales or support, in the reader's words, with plain answers. This is the right place for questions.
- **Final CTA:** one line of value, the same CTA, and risk reversal (trial terms, cancellation, guarantee), all only if true.

## 4. Homepage vs landing page

- **Landing page:** one audience, one message, one action. It matches its traffic source, and it is often longer for colder traffic.
- **Homepage:** leads with the broadest *true* value proposition, then routes visitors by audience or intent ("For agencies", "For in-house teams"). An "ideal for…" line tells readers early whether they're in the right place.

## 5. Feature, pricing and about pages

- **Feature page:** what you can now do → how it works → result → proof → how to try it. Use the name users call the feature.
- **Pricing page:**
  - Answer "which plan is for me?" by naming who each tier is for.
  - Mark the recommended plan.
  - Put billing anxieties right next to the buttons: renewal, cancellation, what happens at the limit, taxes.
  - Plan names and prices must match the user's data exactly.
- **About page:** the founding story only if it connects to the customer's problem. Include who's behind it, with real names if they're public, and a next step.

## 6. Product descriptions (e-commerce)

- Open with who it's for and the main result in one or two sentences.
- Follow with 3–5 scannable bullets. Each starts with the words that carry the benefit and pairs a feature with what it means to the buyer. Put buyers' first questions in the first bullets: size, fit, compatibility, what's in the box.
- Keep specs in a separate, consistent spec list.
- Use sensory and usage detail only if it's true: materials, dimensions, how it feels, how it's made. Facts beat adjectives here more than anywhere ("12 oz waxed canvas, brass rivets" beats "premium quality").
- Show reviews with their source. Never write "customer" quotes.

## 7. App-store listings

Apple:
- name ≤ 30 characters
- subtitle ≤ 30
- promotional text ≤ 170 (can change without review)
- keywords ≤ 100 in total

The first sentence of the description is the one most people see before "more", so make it count. Use the audience's terms. Put awards and press at the end. Don't put prices in the description. Google Play has a short description of about 80 characters. Check current limits before finalizing.

## 8. Meta title and description

- Title about 50–60 characters, description about 150–160, so they aren't truncated.
- Say what the page is and for whom, in plain words. The description is ad copy for the search result: one concrete reason to click, no keyword stuffing.

## 9. Final checks for pages

- [ ] H1 alone tells a stranger what's sold. Subhead makes it believable.
- [ ] Every number, name, logo and quote is from the proof inventory; gaps are `[NEED: …]`.
- [ ] One primary CTA per page; button labels say what happens.
- [ ] Headings make sense when read alone and in order (that's how scanners read).
- [ ] One name per feature across headings, body, buttons and screenshots.
- [ ] Sections differ in length according to importance.
- [ ] No Markdown artifacts if the copy goes into a CMS or HTML; headings are marked as such.
